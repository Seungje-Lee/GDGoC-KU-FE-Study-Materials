터미널 1

터미널이 멈춘 것처럼 보입니다. 이 터미널은 지금 그 컨테이너가 쓰고 있습니다 — 로그가 계속 나오는 게 그 증거입니다. 새 터미널을 하나 더 열어 확인하세요. (끌 때는 Ctrl+C)

Step 2포트 연결 — 구멍을 뚫습니다

터미널 1에서 Ctrl+C 로 끄고, 다시 실행합니다.

터미널 1
docker run --rm -p 8080:80 nginx:alpine
-p 옵션 읽는 법
-p 8080:80
   │    └── 컨테이너 안의 포트
   └─────── 내 노트북의 포트

http://localhost:8080 → nginx 기본 페이지가 뜹니다.

기억할 것

컨테이너는 자기만의 네트워크 공간을 가집니다. 기본적으로 바깥에서 못 들어옵니다. -p 는 “내 노트북 8080으로 들어온 걸 저 컨테이너 80번으로 넘겨라”는 구멍을 뚫는 것입니다. 이 그림이 뒤에서 compose를 이해하는 밑돌이 됩니다.

Step 3내 앱 파일 꽂아넣기 — 그리고 오늘의 문제

터미널 — week4-start 폴더 안에서
docker run --rm -p 8080:80 \
  -v "$(pwd)/dist:/usr/share/nginx/html:ro" \
  nginx:alpine
-v 옵션 읽는 법
-v "$(pwd)/dist : /usr/share/nginx/html : ro"
      │              │                     └── read-only (읽기 전용)
      │              └── 컨테이너 안의 경로
      └── 내 노트북의 경로   ※ 복사가 아니라 "연결" 입니다
🤔 이 명령어를 옆 사람에게 그대로 보내면 될까요?

① 그 사람 컴퓨터에 dist/ 가 없습니다 → 소스 받아서 npm install + npm run build 부터 해야 합니다

② nginx.conf 도 따로 줘야 합니다  ·  ③ 경로가 사람마다 다릅니다

④ 결국 “명령어 + 파일 3개 + 설명서”를 세트로 줘야 합니다

우리가 원하는 것

docker run 내앱 한 줄이면 끝나는 것. 그러려면 dist/ 를 밖에서 꽂아넣는 게 아니라 이미지 안에 넣어야 합니다. 그게 Dockerfile입니다.

2. Dockerfile 4줄 쓰기

한 번에 완성본을 복사하지 마세요

3줄 → 빌드 → 4줄 → 빌드. 매 단계 빌드를 돌려서 레이어가 쌓이는 로그를 직접 보는 것이 이 시간의 목적입니다.

19:35 · Step 13줄로 시작

앱 프로젝트 루트에 Dockerfile 이라는 파일을 만듭니다. 확장자는 없습니다.

Dockerfile (새 파일 · 확장자 없음)
FROM nginx:alpine
COPY dist/ /usr/share/nginx/html/
EXPOSE 80
명령의미
FROM nginx:alpine바닥부터 만들지 않습니다. nginx가 이미 깔린 이미지 위에서 시작
COPY dist/ ...-v 로 꽂는 대신 이미지 안에 복사해 넣습니다 — 오늘의 전환점
EXPOSE 80“이 이미지는 80번을 쓴다”는 문서화. 실제로 여는 건 -p

Step 2설정까지 넣어서 4줄

3회차에 만든 nginx 설정도 이미지 안에 넣습니다. 지금은 컨테이너를 하나만 띄우므로 nginx-solo.conf (SPA fallback + 캐시 헤더, 프록시 없음)를 씁니다 — 이유는 바로 아래에서 설명합니다.

Dockerfile — 한 줄 추가
FROM nginx:alpine
COPY dist/ /usr/share/nginx/html/
COPY nginx-solo.conf /etc/nginx/conf.d/default.conf
EXPOSE 80
🤔 “실행 명령은 안 적나요?”

안 적어도 됩니다. nginx:alpine 이미지 안에 nginx를 실행하는 명령이 이미 들어 있습니다. FROM 으로 그 이미지 위에서 시작했으니 그것도 같이 물려받습니다.

우리가 한 일은 그 위에 내 파일 두 개를 얹은 것이 전부입니다.

3. 빌드하고 띄우기

⚠️ 빌드 전에 한 줄 — .dockerignore 의 dist 를 잠시 끕니다

.dockerignore 에 dist 가 들어 있습니다. 무시된 파일은 애초에 Docker에게 전달되지 않아서 방금 쓴 COPY dist/ 가 "/dist": not found 로 실패합니다. 그 줄 맨 앞에 # 을 붙이세요.

4번 섹션(멀티스테이지)에서 다시 켭니다. 거기서는 컨테이너 안에서 직접 빌드하므로 내 dist 를 보낼 필요가 없습니다 — 그게 이 줄이 원래 있는 이유입니다.

.dockerignore — dist 줄을 이렇게 바꿉니다
# dist
터미널 — Dockerfile이 있는 폴더에서
docker build -t word-app:v1 .
docker run --rm -p 8080:80 --name web word-app:v1
설정 파일이 두 개인 이유 — nginx-solo.conf 와 nginx.conf

방금 넣은 nginx-solo.conf 는 SPA fallback + 캐시 헤더만 있는 설정입니다 (3회차 2단계).

같은 폴더의 nginx.conf 는 3회차 3단계 — /api/ 를 mini-api 로 넘기는 리버스 프록시가 들어 있습니다. 그런데 mini-api 는 compose의 서비스 이름이라서, 컨테이너 하나만 띄우는 지금 그 설정을 쓰면 nginx가 이름을 못 찾고 즉사합니다.

nginx: [emerg] host not found in upstream "mini-api"

그래서 7번 섹션에서 이 한 줄을 nginx.conf 로 갈아끼웁니다. 3회차에 설정을 1→2→3단계로 갈아끼운 것과 똑같습니다.

명령어 읽는 법
docker build -t word-app:v1 .
             │                 └── 빌드 컨텍스트 (이 폴더를 Docker에게 넘긴다)
             └── 이미지에 이름:태그 를 붙인다

http://localhost:8080 → -v 없이 내 앱이 뜹니다. /about 을 새로고침해도 404가 안 납니다. 설정까지 이미지 안에 들어갔기 때문입니다.

지금 이게 무슨 의미인지

방금 만든 이미지는 여러분 앱을 통째로 담고 있습니다. 이걸 이미지 저장소에 올리면 지구 반대편 서버가 docker run 내앱 한 줄로 똑같은 화면을 띄웁니다. Node.js도, nginx 설치도, 빌드도 필요 없습니다. 이미 다 안에 들어 있으니까요.

컨테이너는 마법이 아니라 작은 리눅스입니다. 들어가서 볼 수 있습니다.

.dockerignore 가 .env 를 제외하기 때문에 도커 빌드에는 내 .env 값이 아예 들어오지 않습니다. 그래서 지금 박힌 값은 코드의 기본값인 상대경로(/api/words)입니다. 6번 섹션에서 이 값을 빌드 시점에 갈아끼웁니다.

자주 나는 에러

Cannot connect to the Docker daemon

원인: Docker Desktop이 실행되지 않았습니다. 오늘 가장 흔한 1번 에러입니다.

해결: Docker Desktop을 실행하고 고래 아이콘이 안정될 때까지 기다린 다음 다시 시도하세요. (Docker는 백그라운드 데몬이 떠 있어야 CLI 명령이 동작합니다)

확인
docker ps        ← 에러 없이 표 머리글이 나오면 준비 완료
Bind for 0.0.0.0:8080 failed: port is already allocated

원인: 그 포트를 이미 다른 프로그램이나 컨테이너가 쓰고 있습니다.

해결 두 가지 — 왼쪽(호스트) 숫자만 바꾸거나, 쓰고 있는 컨테이너를 정리합니다.

고치는 법
docker run --rm -p 8081:80 word-app:v1   ← 왼쪽만 바꾼다

docker ps                # 누가 쓰는지 확인
docker stop <이름>        # 정지

-p 의 오른쪽(컨테이너 안 포트)은 바꾸면 안 됩니다. nginx는 80을 듣고 있으니까요.

failed to solve: "/dist": not found

원인 1: docker build 를 엉뚱한 폴더에서 쳤습니다. 마지막 . 이 빌드 컨텍스트입니다. Dockerfile 이 있는 폴더에서 치세요.

원인 2: .dockerignore 에 dist 가 들어 있습니다. 무시된 파일은 애초에 Docker에게 전달되지 않아서 COPY 가 실패합니다. (3번 섹션에서는 dist 줄을 잠시 주석 처리하세요. 4번 섹션 멀티스테이지로 넘어가면 다시 켜면 됩니다)

컨테이너가 뜨자마자 바로 종료됩니다

컨테이너 안에서 돌던 프로그램이 어떤 이유로든 종료되면 컨테이너도 함께 끝납니다. 그래서 “왜 종료됐는지”를 로그에서 찾는 것이 먼저입니다.

진단은 항상 로그부터:

디버깅 1순위
docker ps -a          # 죽은 컨테이너까지 보기
docker logs <이름>     # 무슨 말을 남기고 죽었는지

오늘 이 증상의 1순위 원인은 nginx 설정입니다. 로그에 이 줄이 보이면 nginx.conf(프록시 버전)를 넣고 컨테이너를 혼자 띄운 것입니다.

nginx: [emerg] host not found in upstream "mini-api"

Dockerfile 의 COPY 줄을 nginx-solo.conf 로 바꿔 다시 빌드하세요. mini-api 는 7번 섹션 compose에서 등장합니다.

그 줄이 아니라면 — 설정 파일 문법 오류(로그에 줄 번호가 나옵니다)이거나, Node 앱이라면 서버가 listen 을 안 했을 가능성이 큽니다. --rm 으로 띄운 컨테이너는 죽는 순간 지워져 docker logs 가 안 되므로, 실행한 터미널의 로그를 위로 스크롤해서 보세요.

4. 빌드를 내 노트북이 아니라 컨테이너가 하게 하기

20:20 · 15분“제 컴퓨터에선 빌드 되는데요”를 없애는 방법

먼저 — 이게 왜 프론트엔드 문제인가

지금 우리 Dockerfile은 COPY dist/ 로 시작합니다. 그럼 그 dist/ 는 누가 만들었죠? 내 노트북이 만들었습니다. 그 말은 이미지 안의 결과물이 내 Node 버전, 내 node_modules, 내가 마지막으로 저장한 상태에 의존한다는 뜻입니다.

프론트엔드 팀에서 실제로 이렇게 터집니다.

  • 팀원 A는 Node 18, 나는 Node 22 — 빌드 결과물이 미묘하게 다릅니다
  • npm install 을 각자 다른 시점에 해서 lock 파일과 실제 설치 버전이 어긋납니다
  • 급해서 npm run build 를 깜빡하고 어제 dist/ 를 그대로 배포합니다

해결은 하나입니다 — 빌드를 사람 손에서 뺍니다. 소스코드만 주면 누가 언제 실행해도 같은 결과가 나오게 만드는 것. 그게 지금부터 할 일입니다.

📸 그런데 이건 이미 아는 이야기입니다

Vercel에 push 하면 무슨 일이 일어나던가요?

Vercel 서버가 내 소스를 받아서 거기서 npm ci && npm run build 를 돌립니다. 내 dist/ 를 올리는 게 아닙니다. GitHub Actions도, GitLab CI도 전부 같습니다.

지금부터 만드는 것이 정확히 그 동작입니다. “빌드 환경까지 포함해서 배포한다” — Vercel이 대신 해주던 일 중 두 번째를 오늘 직접 만듭니다.

방법 — FROM 을 두 번 씁니다

Dockerfile 하나 안에 빌드용 환경과 실행용 환경을 따로 두고, 결과물만 옮겨 담습니다. 이걸 멀티스테이지 빌드라고 부릅니다.

Dockerfile — 통째로 이렇게 바꿉니다
// ---- 1단계: 빌드 (작업대. 결과물만 남기고 통째로 버려집니다) ----
FROM node:20-alpine AS builder
WORKDIR /app

// package.json 을 먼저 복사하는 이유는 아래에서 설명합니다
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build        // ← 내 노트북이 아니라 여기서 빌드됩니다

// ---- 2단계: 실행 (실제로 배포되는 것은 여기부터) ----
FROM nginx:alpine
COPY --from=builder /app/dist/ /usr/share/nginx/html/
COPY nginx-solo.conf /etc/nginx/conf.d/default.conf
EXPOSE 80
읽을 줄은 딱 두 개입니다

AS builder — 1단계에 이름을 붙입니다.

COPY --from=builder /app/dist/ — 1단계에서 만든 dist/ 만 꺼내옵니다. 1단계의 Node도, node_modules 도, 소스코드도 최종 이미지에 안 들어갑니다.

나머지 줄은 3회차에 터미널에서 치던 것과 같습니다 — npm ci, npm run build. 새로 배우는 명령어가 아닙니다.

빌드 전에 — .dockerignore 의 dist 를 다시 켜세요

§3에서 # dist 로 주석 처리했던 그 줄입니다. # 을 떼서 원래대로 되돌립니다.

이제는 컨테이너 안에서 빌드하니 내 dist 를 보낼 이유가 없습니다. 오히려 보내면 COPY . . 로 옛날 dist 가 딸려 들어갑니다. §3에서는 걸림돌이던 그 한 줄이, 여기서는 있어야 맞는 줄입니다.

터미널 — 이제 dist/ 를 미리 안 만들어도 됩니다
docker build -t word-app:v3 .
지금 일어난 일 — 이것이 오늘 이 구간의 전부입니다

내 노트북에서 npm run build 를 한 번도 안 했는데 앱이 배포됐습니다. node_modules 를 지우고 다시 해봐도 똑같이 됩니다.

이제 이 저장소를 받은 사람은 누구든 docker build 한 줄이면 같은 결과를 얻습니다. Node를 깔 필요도, 버전을 맞출 필요도 없습니다.

왜 package.json 을 먼저 복사했나 — 30초짜리 이야기

소스코드를 한 줄만 고치고 다시 빌드해 보세요. 로그에 이 줄이 보입니다.

빌드 로그
=> CACHED [builder 3/6] RUN npm ci      ← 다시 안 돌았습니다
한 줄 요약

Docker는 명령 한 줄마다 결과를 캐시합니다. 어떤 줄의 입력이 바뀌면 그 줄부터 아래만 다시 실행됩니다.

그래서 자주 바뀌는 것(소스코드)을 뒤로, 잘 안 바뀌는 것(의존성 목록)을 앞으로 둡니다. 반대로 COPY . . 를 맨 위에 두면 한 글자만 고쳐도 매번 npm ci 를 다시 돕니다. 빌드가 10초에서 2분이 됩니다.

사용자에게 실제로 전달되는 건 dist/ 150KB 입니다. 나머지는 전부 빌드에만 필요했던 것입니다.

그리고 크기보다 중요한 것 — 275MB 쪽은 소스코드 전체가 프로덕션 서버에 올라가 있습니다. --from=builder 한 줄이 그걸 막습니다.

6. ARG 로 환경변수 주입 — 3회차 함정의 해법

지난주에 일부러 남겨둔 숙제입니다

3회차에 “.env 를 바꿀 때마다 재빌드해야 한다”를 확인했고, “그럼 환경별로 어떻게 하나”는 다음 주에 직접 만든다고 하고 넘어갔습니다. 오늘입니다.

오늘 가장 프론트엔드다운 구간입니다. VITE_·NEXT_PUBLIC_ 은 우리가 매일 쓰는 것이고, “환경변수 바꿨는데 왜 안 먹죠?” 는 프론트엔드 채널에 가장 자주 올라오는 질문입니다.

20:35 · Step 1먼저 문제를 재현합니다

터미널 1 — 실행 시점에 환경변수를 넣어봅니다
docker run --rm -p 8080:80 --name web \
  -e VITE_API_URL=https://런타임에바뀔까.com \
  word-app:v3
터미널 2 — 이미지 안의 JS를 열어봅니다
docker exec -it web sh -c "grep -o '런타임에바뀔까' /usr/share/nginx/html/assets/*.js | head"
docker exec -it web sh -c "grep -o '/api/words'     /usr/share/nginx/html/assets/*.js | head"
여전히 옛날 값입니다 — -e 는 아무 일도 하지 않았습니다

컨테이너 안에 환경변수는 분명히 들어 있습니다. env 를 치면 보입니다.

그런데 그걸 읽을 사람이 없습니다. dist/ 는 이미 구워진 파일이니까요. 3회차에 grep 으로 확인한 바로 그 사실입니다.

Step 2해법 — 빌드 시점에 넣습니다

Dockerfile — builder 스테이지의 RUN npm run build 앞에 추가
# Vite 는 import.meta.env 값을 빌드 시점에 코드로 박아 넣습니다.
# 따라서 이 값은 반드시 "빌드하는 동안" 존재해야 합니다.
# 런타임 환경변수(-e / environment:)는 무시됩니다.
ARG VITE_API_URL=/api
ENV VITE_API_URL=$VITE_API_URL

RUN npm run build
언제 존재하나누가 읽나
ARGdocker build 동안만Dockerfile 내부. 최종 이미지에 안 남는다
ENV빌드 + 실행 내내그 안에서 도는 프로세스

ARG 로 받은 값을 ENV 로 옮겨야 RUN npm run build 안에서 도는 Vite 프로세스가 그 값을 봅니다.

Step 3같은 소스코드, 다른 이미지 두 개

터미널
docker build -t word-app:stg  --build-arg VITE_API_URL=https://stg.example.com .
docker build -t word-app:prod --build-arg VITE_API_URL=https://api.example.com .
각각 확인 — 다른 주소가 박혀 있습니다
docker run --rm word-app:stg  sh -c "grep -o 'https://stg[^\"]*' /usr/share/nginx/html/assets/*.js | head -1"
docker run --rm word-app:prod sh -c "grep -o 'https://api[^\"]*' /usr/share/nginx/html/assets/*.js | head -1"
📸 이 결론을 남겨두세요

ARG → docker build 시점 → Vite가 읽는다 ✅

ENV / -e → docker run 시점 → 아무도 안 읽는다 ❌

내 프레임워크가 환경변수를 ‘언제’ 읽는지 알아야, 값을 ‘어느 시점’에 보낼지 정할 수 있습니다.

Vercel 대시보드에서 환경변수를 바꾸면 자동으로 재배포가 도는 이유가 이것입니다. 재빌드 없이는 반영될 방법이 없으니까요. 그동안 Vercel이 대신 눌러주던 것을 방금 직접 만든 겁니다.

7. docker compose — 앱과 API를 한 세트로

20:55 · 15분🟡 파일은 드립니다. 실행하고 두 가지만 이해하면 됩니다

먼저 — 이게 왜 프론트엔드 문제인가

Vercel은 프론트엔드만 호스팅합니다. 그런데 우리 앱은 혼자 못 돕니다 — 단어 목록을 주는 API가 옆에 떠 있어야 화면이 채워집니다.

지금까지 우리는 그걸 터미널 두 개로 해결했습니다. 앱 하나, API 하나. 그런데 이걸 남에게 넘길 때 문제가 됩니다 — “API부터 켜세요”, “포트는 3001이에요”, “순서 지켜주세요”를 말로 전달해야 합니다.

compose는 그 구두 전달을 파일 하나로 바꾸는 도구입니다. 오늘은 문법을 외우지 않습니다. 실행해서 동작을 보고, 두 가지만 가져갑니다.

Step 1 — Dockerfile의 nginx 설정을 되돌립니다

이제 mini-api와 함께 뜨므로, 3회차 3단계 설정(/api/ 리버스 프록시)을 쓸 수 있습니다.

Dockerfile — COPY 한 줄만 바꿉니다
// 지금까지 (§2~§6)
COPY nginx-solo.conf /etc/nginx/conf.d/default.conf

// 여기서부터
COPY nginx.conf /etc/nginx/conf.d/default.conf

Step 2 — 한 줄로 띄웁니다

docker-compose.yml 은 저장소 docker/ 폴더에 이미 들어 있습니다. 직접 쓰지 않습니다. 그 폴더로 가서 실행만 하세요.

터미널
cd docker
docker compose up --build

http://localhost:8080 → 앱도, 추천 단어 목록도 정상. CORS 에러 없음. 터미널은 하나입니다.

가져갈 것 ① — 프론트와 API가 같은 출처가 됩니다

3회차에 했던 그 이야기가 여기서 완성됩니다

브라우저가 아는 주소는 http://localhost:8080 하나뿐입니다. 화면도 거기서, /api/words 도 거기서 받습니다.

그래서 CORS 검사가 애초에 일어나지 않습니다. 3회차에 nginx 설정 몇 줄로 만든 그 구조를, 이제 파일 하나가 매번 똑같이 재현해 줍니다.

가져갈 것 ② — ports 가 없는 서비스는 바깥에서 안 보입니다

직접 확인해 보세요
curl http://localhost:3001/api/words    // 실패합니다
curl http://localhost:8080/api/words    // 잘 됩니다
⚠️ 3001이 성공하면 — 옛날 node server.js 가 아직 떠 있는 것입니다

3회차에 직접 띄운 미니 API를 안 끄셨다면 그게 응답합니다. compose가 띄운 컨테이너가 아닙니다. 그 터미널에서 Ctrl+C 로 끄고 다시 해보세요. (lsof -i :3001 로 누가 쓰는지 확인할 수 있습니다)

🤔 같은 서버인데 왜 하나는 되고 하나는 안 되나

docker-compose.yml 의 mini-api 에는 ports 가 없습니다. 일부러입니다. 고장난 게 아닙니다.

ports 는 컨테이너끼리 통신하기 위한 설정이 아니라, 바깥 세상(내 컴퓨터)에 구멍을 뚫을 때만 필요합니다. web(nginx)은 같은 네트워크 안에 있으니 mini-api 라는 이름으로 그냥 접근합니다.

실무에서 DB나 내부 API를 정확히 이렇게 배치합니다 — 외부에 열린 입구는 nginx 하나뿐입니다.

설정 파일 전문이 궁금하신 분만 — docker/docker-compose.yml

오늘 외울 필요는 없습니다. “이런 걸 적어두는 파일이구나” 정도로 보세요. context: 는 “이 폴더의 Dockerfile로 빌드해라”, depends_on: 은 “얘부터 뜨고 나서”라는 뜻입니다.

docker/docker-compose.yml
services:
  web:
    build:
      context: ../week4-start
      args:
        VITE_API_URL: /api        // ← 방금 배운 빌드 시점 주입
    ports:
      - "8080:80"
    depends_on:
      mini-api:
        condition: service_healthy

  mini-api:
    build:
      context: ../mini-api
    // ports 가 없습니다 — 일부러입니다
    healthcheck:
      test: ["CMD","wget","-q","-O","-","http://127.0.0.1:3001/api/health"]
      interval: 5s
      retries: 5

nginx.conf 의 proxy_pass http://mini-api:3001; 에서 mini-api 는 이 파일의 서비스 이름입니다. compose가 서비스 이름을 그대로 호스트 이름으로 만들어 줍니다 — 컨테이너끼리는 IP가 아니라 이름으로 대화합니다.

정리
docker compose down
🎉 이게 오늘 확장 파트의 결론입니다

명령어 한 줄입니다. docker compose up.

새로 온 팀원이 첫날 이 한 줄로 전체 스택을 띄웁니다. 설치 문서도, “먼저 API부터 켜세요” 같은 구두 전달도 필요 없습니다. 환경 구성이 문서가 아니라 코드가 된 겁니다.

자주 나는 에러

dependency failed to start: container study-mini-api is unhealthy

가장 흔한 원인 — 헬스체크가 localhost 를 쓰고 있습니다. 실제로 겪은 함정입니다.

Alpine 안에서 localhost 는 IPv6 주소 ::1 로 먼저 해석됩니다. 그런데 서버는 IPv4 0.0.0.0 에만 바인딩하므로 Connection refused 가 나고 컨테이너가 unhealthy 가 됩니다. 서버는 멀쩡한데 헬스체크만 실패하는, 찾기 아주 어려운 종류의 버그입니다.

고치는 법
test: ["CMD","wget","-q","-O","-","http://localhost:3001/api/health"]   ← ::1 로 감
test: ["CMD","wget","-q","-O","-","http://127.0.0.1:3001/api/health"]   ← 이렇게

진단: docker compose logs mini-api 로 서버 자체는 떴는지 먼저 확인하세요. 서버 로그는 정상인데 unhealthy 면 십중팔구 이것입니다.

host not found in upstream "mini-api" — nginx가 시작하자마자 죽습니다

원인: nginx는 시작할 때 proxy_pass 의 호스트 이름을 한 번 해석합니다. 그때 mini-api 가 없으면 nginx가 아예 시작되지 않습니다.

해결:

  • depends_on 에 condition: service_healthy 를 넣습니다 (위 파일에 이미 있습니다)
  • 서비스 이름과 proxy_pass 의 호스트가 철자까지 같은지 확인
  • compose 없이 web 컨테이너만 단독으로 띄우면 반드시 이 에러가 납니다. 그때는 nginx.conf 의 location /api/ 블록을 잠시 주석 처리하세요

참고: depends_on 만 넣으면 “시작 순서”만 보장되고 “준비 완료”는 보장되지 않습니다. 그래서 healthcheck + condition: service_healthy 가 필요합니다.

코드를 고쳤는데 반영이 안 됩니다 / docker-compose 명령이 없다고 나옵니다

반영 안 됨: --build 없이 up 했습니다. → docker compose up --build

명령이 없음: docker-compose(하이픈)는 v1 문법입니다. docker compose — 하이픈 없이 띄어쓰기로 쓰세요 (v2).

컨테이너끼리 통신 안 됨: localhost 로 부르고 있을 가능성이 큽니다. 컨테이너 안의 localhost 는 자기 자신입니다. 서비스 이름을 쓰세요.

여기부터는 타이핑을 많이 안 하셔도 됩니다

오늘의 결과물은 이미 여러분 노트북에 있습니다. 지금부터는 왜 다들 Next.js를 쓰는가를 이해하는 시간입니다. 단, 아래 curl 두 줄은 꼭 직접 쳐보세요. 오늘 심화의 문입니다.

1회차에 “페이지 소스 보기”를 했더니 빈 <div id="root"> 만 있었죠. 3회차에 dist/index.html 을 열었더니 거기도 빈 <div id="root"> 였고요. 오늘 그게 무슨 의미인지 확인합니다.

터미널 — compose를 띄운 상태에서
cd docker && docker compose up -d --build
curl -s http://localhost:8080 | head -20
출력 — 서버가 실제로 보낸 것
<!doctype html>
<html lang="ko">
  <head>
    <title>나만의 단어장</title>
    <script type="module" crossorigin src="/assets/index-C7xK9pQr.js"></script>
  </head>
  <body>
    <div id="root"></div>          ← 이게 전부입니다
  </body>
</html>
단어가 몇 개나 들어 있는지 세어봅니다
curl -s http://localhost:8080 | grep -o "serendipity" | wc -l
결과: 0

단어가 하나도 없습니다. curl 은 JavaScript를 실행하지 않으니까요. 화면에는 카드가 잔뜩 보이는데 서버가 보낸 HTML에는 내용이 없습니다. 이것이 CSR(Client-Side Rendering)입니다.

⚠️ 개발자도구 Elements 탭과 혼동하지 마세요

페이지 소스 보기(Cmd/Ctrl + U) = 서버가 보낸 원본

개발자도구 Elements 탭 = JS 실행 후의 지금 화면(DOM)

Elements에서는 CSR 앱에서도 내용이 보입니다. 이 둘을 구분 못 하면 아래 SSR 비교가 전부 무너집니다.

9. [심화] Next.js SSR HTML과 비교하기

Next.js 완성본은 미리 드립니다. 오늘은 Next.js 문법 강의가 아니라 서버가 보내는 HTML이 어떻게 달라지는지를 보는 시간입니다.

터미널 1 — 완성본 실행
cd next-version      # 저장소 루트에 있습니다 (4회차 자료와 함께 공개)
npm install
npm run dev
터미널 2 — 같은 명령을 3000번 포트에
curl -s http://localhost:3000 | grep -o "serendipity" | wc -l
curl -s http://localhost:3000 | head -40
출력
11      ← 0 이 아니라는 점이 핵심입니다

<main>
  <section class="plain-list">
    <h2>추천 단어</h2>
    <ul>
      <li>serendipity — 뜻밖의 행운</li>
      <li>ubiquitous — 어디에나 있는</li>

Next.js는 HTML을 한 줄로 보냅니다. grep -c 는 “매칭된 줄 수”를 세므로 항상 1이 나옵니다. 반드시 grep -o "단어" | wc -l 를 쓰세요.

Next.js를 쓴다고 자동으로 SSR이 아닙니다

'use client' 안에서 useEffect 로 데이터를 받으면 Next.js에서도 curl 결과가 비어 있습니다. 프레임워크를 쓰는 것과 그 기능을 쓰는 것은 다릅니다.

10. [심화] standalone 으로 Next.js 배포하기

이 섹션은 강사 데모입니다 — 파일은 전부 드립니다

따라 치지 않으셔도 됩니다. “무엇이 달라지는가”만 보세요.

3회차까지 배포한 것은 파일이었습니다. 지금 배포하는 것은 프로세스입니다. 이게 결정적인 차이입니다.

next.config.js — 이 한 줄이 전부입니다
/** @type {import('next').NextConfig} */
const nextConfig = {
  output: 'standalone',
  reactStrictMode: true,
};

module.exports = nextConfig;
standalone 이 하는 일

“이 앱을 실제로 돌리는 데 필요한 것만 골라서 한 폴더에 모아라”는 옵션입니다. node_modules 전체(수백 MB)가 아니라 실제로 import되는 것만 추려서 담습니다.

그리고 .next/standalone/server.js 라는 실행 파일이 하나 생깁니다. 이게 우리의 웹서버입니다.

Dockerfile — runner 스테이지 (마지막이 nginx가 아니라 node 입니다)
FROM node:20-alpine AS runner
WORKDIR /app
ENV NODE_ENV=production

# standalone 은 "실행에 필요한 것"만 담습니다.
# public/ 과 .next/static 은 포함되지 않아 반드시 따로 복사해야 합니다.
COPY --from=builder /app/public ./public
COPY --from=builder /app/.next/standalone ./
COPY --from=builder /app/.next/static ./.next/static

ENV PORT=3000
ENV HOSTNAME=0.0.0.0
EXPOSE 3000

CMD ["node", "server.js"]   ← next start 가 아닙니다
docker/docker-compose.next.yml — 저장소에 완성본이 있습니다
services:
  next:
    build: ./next-version
    expose:
      - "3000"          # 바깥에 직접 열지 않습니다. nginx 를 통해서만

  gateway:
    image: nginx:alpine
    ports:
      - "80:80"
    volumes:
      - ./gateway.nginx.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on:
      - next
gateway.nginx.conf 도 저장소에 있습니다

docker/gateway.nginx.conf — 열어보면 location /_next/static/ 에 1년 캐시 헤더가 붙어 있습니다. 3회차의 /assets/ 캐시 헤더와 똑같은 논리입니다 (해시가 붙은 파일이니 영구 캐시해도 안전).

차이는 root 가 없다는 것입니다. 파일을 주는 게 아니라 proxy_pass http://next_app 으로 전부 넘깁니다.

확인
docker compose up --build
curl -s http://localhost | grep -o "serendipity" | wc -l
nginx의 역할이 바뀌었습니다

nginx는 이제 파일을 주는 역할이 아니라 문지기입니다 — HTTPS 종료, 압축, 캐시 헤더, 정적 자산 처리, 그리고 Node 프로세스를 바깥에 직접 노출하지 않기.

3회차의 nginx 지식이 버려진 게 아니라 역할이 바뀌어 계속 쓰입니다.

자주 나는 에러

standalone 인데 CSS가 전부 깨집니다 / 이미지가 404 입니다

오늘 Next.js 파트에서 가장 흔한 사고입니다.

.next/standalone 폴더는 “서버 실행에 필요한 것”만 담습니다. 해시가 붙은 JS·CSS 청크(.next/static)와 public/ 은 포함되지 않습니다. 그래서 Dockerfile에서 수동으로 복사해야 합니다.

이 두 줄이 없으면 깨집니다
COPY --from=builder /app/.next/static ./.next/static   ← 빠뜨리면 CSS·JS 깨짐
COPY --from=builder /app/public ./public               ← 빠뜨리면 이미지 404

증상 구분: 페이지 자체는 뜨는데 스타일만 없다 → static 미복사. 특정 이미지만 404 → public 미복사.

"/app/.next/standalone": not found

원인: next.config.js 에 output: 'standalone' 이 없습니다. 그러면 그 폴더 자체가 생성되지 않습니다. 4회차 실수 1위입니다.

해결: 설정을 추가하고 다시 빌드한 뒤, ls .next/standalone 으로 폴더가 생겼는지 확인하세요.

-p 로 포트를 뚫었는데 접속이 안 됩니다

원인: 앱이 컨테이너 안에서 127.0.0.1 에만 바인딩하고 있습니다. 그러면 컨테이너 바깥에서 오는 연결을 아예 받지 못합니다.

고치는 법
ENV HOSTNAME=0.0.0.0              Next.js standalone
--host 0.0.0.0                     Vite preview 등

포트를 아무리 뚫어도 앱이 안 듣고 있으면 소용없습니다. 매년 나오는 사고입니다.

platform mismatch / exec format error (M1·M2 맥)

증상: The requested image's platform (linux/amd64) does not match the detected host platform (linux/arm64/v8) 또는 실행하자마자 exec format error.

원인: Apple Silicon(arm64)에서 만든 이미지를 x86 서버에 올렸거나, 그 반대입니다. CPU 명령어 세트가 달라서 그대로는 못 돕니다.

해결 — 배포 대상 아키텍처를 명시해서 빌드
# 서버가 x86(대부분의 클라우드)인 경우
docker build --platform linux/amd64 -t word-app:v3 .

# 실행할 때만 임시로 맞추기 (느립니다 — 에뮬레이션)
docker run --platform linux/amd64 --rm -p 8080:80 word-app:v3

수업 중에는 내 노트북에서만 돌리므로 신경 쓰지 않아도 됩니다. 실제 서버에 올릴 때 반드시 기억해야 하는 항목입니다.

디스크가 꽉 찼습니다 (no space left on device)

오늘 이미지를 여러 개 만들었으니 그럴 수 있습니다. 먼저 얼마나 먹었는지 확인하세요.

확인 후 정리
docker system df           # 얼마나 먹었나
docker system prune         # 안 쓰는 컨테이너·네트워크·캐시 정리
docker system prune -a      # 이미지까지 전부 (주의: 다시 받아야 함)

-a 는 주의하세요. node:20-alpine, nginx:alpine 도 지워지고 다시 받아야 합니다. 수업 중에는 -a 없이 먼저 시도하세요.

# 나만의 단어장 — 배포

## 로컬 실행
docker compose up --build   # http://localhost:8080

## 구조
- web: Vite 빌드 → nginx (멀티스테이지, 약 92MB)
- mini-api: Node 20 미니 API (포트 3001, 외부 미노출)

## 왜 이렇게 했나
- API 주소는 build arg 로 주입 — VITE_* 는 빌드 시점에 코드로 박히기 때문
- SPA fallback (try_files) — 클라이언트 라우트 새로고침 시 404 방지
- /api 는 nginx 리버스 프록시 — 같은 출처가 되어 CORS 미발생
- 멀티스테이지 — 최종 이미지에 Node·node_modules·소스코드를 남기지 않음

## 이 프로젝트에 Next.js를 쓰지 않은 이유
(판단 기준표로 각자 작성)
마지막 항목이 핵심입니다
