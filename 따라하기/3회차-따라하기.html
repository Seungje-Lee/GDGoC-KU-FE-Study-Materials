빌드와 웹서버

오늘은 내가 만든 앱에 주소가 생기는 날입니다. npm run build 가 만든 폴더를 직접 열어보고, 그것을 웹서버 위에 올려 사람이 접속할 수 있는 주소로 만듭니다.

오늘의 진행 방식

오늘 키보드로 치는 것은 터미널 명령어뿐입니다. 코드가 필요한 곳은 전부 복사 버튼 한 번으로 끝냅니다. 대신 명령어 하나하나가 뒤에서 무슨 일을 벌이는지 그림으로 이해하는 것이 오늘의 목표입니다.

오늘은 “에러를 일부러 만드는 날”입니다. 404도, 흰 화면도, CORS 에러도 전부 계획된 것입니다. 에러가 안 나면 오히려 설정이 안 붙은 것이니 손을 들어주세요.

Docker 명령어는 오늘 뜻을 몰라도 됩니다. “nginx를 설치하지 않고 빌려 쓰는 방법”이라고만 알아두세요. 다음 주 3시간이 통째로 그 설명입니다.

2. dist/ 열어보기

19:25 · 20분VS Code 말고 파일 탐색기로 여세요

터미널 — 운영체제에 맞는 한 줄
open dist          # macOS
explorer dist      # Windows
xdg-open dist      # Linux
왜 굳이 파일 탐색기인가

IDE 안에서 보면 여전히 “코드”로 느껴집니다. 파일 탐색기로 열면 USB에 복사해서 옮길 수 있는 물건이라는 실체감이 생깁니다. 그 실체감이 오늘 전체의 토대입니다.

dist/ — 폴더 1개, 파일 3개. 이게 전부입니다
dist/
├── index.html                      ← 1회차의 그 파일
└── assets/
    ├── index-DkR2mQ8a.css             내 CSS 전부가 여기
    └── index-C7xK9pQr.js            ← 내 JSX 전부가 여기

node_modules 도, src/ 도, package.json 도 없습니다. 이 폴더만 통째로 옮겨도 그대로 동작합니다.

① dist/index.html 을 에디터로 열어 직접 읽으세요

dist/index.html — 빌드된 결과물
<!doctype html>
<html lang="ko">
  <head>
    <title>나만의 단어장</title>
    <script type="module" crossorigin src="/assets/index-C7xK9pQr.js"></script>
    <link rel="stylesheet" crossorigin href="/assets/index-DkR2mQ8a.css">
  </head>
  <body>
    <div id="root"></div>          ← 빌드해도 그대로입니다
  </body>
</html>
1회차 복선 회수

1회차에서 “페이지 소스 보기 했더니 빈 div 뿐”이라고 했던 그것입니다. 빌드된 결과물에도 여전히 빈 div 입니다. 단어는 한 글자도 없습니다. 이 HTML이 4회차 SSR 비교의 대조군입니다.

그리고 src="/assets/..." 는 맨 앞에 슬래시가 있는 절대 경로입니다. 이게 잠시 뒤 3번 섹션에서 문제가 됩니다. 지금 손가락으로 짚어두세요.

② dist/assets/index-*.js 를 열어보세요

에디터로 열고 Cmd/Ctrl + F 로 내 컴포넌트에 있던 한글 문자열(예: 나만의 단어장, 내 단어장에 추가)을 찾아보세요. 찾아집니다.

변환무슨 일눈으로 확인하는 법
번들링수십 개 파일을 하나로 합침파일 개수가 줄었다
트랜스파일JSX → React.createElement 호출로 번역파일 안에 <div> 가 없다
미니파이변수명을 a, b 로 줄이고 공백·주석 제거줄바꿈이 거의 없다

WordCard.jsx 라는 파일은 dist/ 안에 없습니다. 다른 컴포넌트들과 함께 알아볼 수 없게 뭉쳐져 있을 뿐, 사라진 게 아닙니다.

③ 파일명 뒤의 C7xK9pQr 는 왜 붙나

파일 내용을 요약한 콘텐츠 해시입니다. 내용이 1바이트만 바뀌어도 이 문자열이 통째로 바뀝니다.

해시가 없다면 벌어지는 일
월  사용자가 index.js 를 내려받음 → 브라우저가 캐시에 저장
화  내가 버그를 고쳐서 배포. 파일명은 여전히 index.js
화  사용자 접속 → 브라우저: "어제 받아둔 거 있는데?"
    → 사용자는 어제의 버그를 그대로 본다  ❌

─────────────────────────────────────────────

월  index-C7xK9pQr.js 를 내려받아 캐시
화  내용이 바뀌면 파일명도 바뀜 → index-A3mN1zTb.js
화  index.html 이 새 파일명을 가리킴 → 캐시에 없음 → 새로 받음
    → 고친 게 반영된다  ✅
그럼 index.html 은요? 걔는 해시가 없는데?

맞습니다. index.html 은 절대 캐시하면 안 되는 파일입니다. 나머지 전부의 “목차”이기 때문입니다. 오늘 9번 섹션에서 이걸 nginx 설정으로 직접 표현합니다.

file:// 은 파일을 연다. http:// 는 서버에게 요청한다.

추천 단어 영역 붙이기 — 복사 버튼으로 한 번에

미니 API에서 단어 목록을 받아오는 컴포넌트를 붙입니다. 직접 타이핑하지 않습니다. 2회차에 배운 fetch + useEffect 그대로라 새 문법이 없으니, 아래 두 블록을 복사해서 그대로 붙여넣으세요. 10번 섹션에서 이 컴포넌트가 CORS 에러를 일으킬 겁니다 — 그게 이 컴포넌트의 존재 이유입니다.

src/components/RecommendedWords.jsx (새 파일)
import { useEffect, useState } from 'react'

const API_BASE = (import.meta.env.VITE_API_URL ?? '').trim().replace(/\/+$/, '')

export default function RecommendedWords() {
  const [words, setWords] = useState([])
  const [error, setError] = useState(null)

  useEffect(() => {
    fetch(`${API_BASE}/api/words`)
      .then((r) => r.json())
      .then(setWords)
      .catch((e) => setError(e.message))
  }, [])

  if (error) return <p style={{ color: 'crimson' }}>추천 단어를 불러오지 못했습니다: {error}</p>

  return (
    <section>
      <h2>추천 단어</h2>
      <ul>
        {words.map((w) => (
          <li key={w.word}>{w.word} — {w.meaning}</li>
        ))}
      </ul>
    </section>
  )
}
src/App.jsx — 두 줄만 추가합니다
// ① 맨 위 import 에 한 줄
import RecommendedWords from './components/RecommendedWords.jsx'

// ② return 안, 목록 아래쯤에 한 줄
<RecommendedWords />
미니 API가 돌려주는 단어의 모양

id 가 없습니다. 그래서 key 는 w.word 를 씁니다.

로딩·에러·빈 목록까지 3-state로 다룬 완성본은 week4-start/src/hooks/useApiWords.js 와 week4-start/src/components/RecommendedWords.jsx 에 있습니다.

console.log(import.meta.env.VITE_API_URL);  // "http://localhost:3001"  ← 나온다
console.log(import.meta.env.API_SECRET);    // undefined                ← 안 나온다
그래서 VITE_ 에는 절대 비밀을 넣지 않습니다

.env 에는 DB 비밀번호도 들어갈 수 있습니다. Vite가 그걸 전부 번들에 넣으면 그 순간 전 세계에 공개됩니다. 그래서 “VITE_ 를 붙인 것 = 공개돼도 되는 것”이라고 개발자가 명시적으로 선언하게 만듭니다.

VITE_OPENAI_API_KEY=sk-... 는 방금 grep 으로 봤듯이 번들에 평문으로 박힙니다. 개발자도구만 열면 누구나 봅니다.

그래서 “빌드는 한 번, 배포는 여러 곳”이 불가능합니다

개발·스테이징·운영에서 API 주소가 다르면 환경마다 다시 빌드해야 합니다. 같은 코드인데 결과물이 세 개입니다.

“그럼 어떻게 해요?” — 해법은 다음 주에 직접 만듭니다 (--build-arg). 오늘은 문제를 정확히 아는 것까지가 목표입니다.

✅ 오늘 가장 중요한 구간 — 여기까지 확인

6. 웹서버가 하는 일 — nginx를 만나기 전에

20:55 · 10분🔵 여기서는 손을 쓰지 않습니다 — 그림으로 이해하는 파트

지금까지를 정리하면 — npm run build 가 파일 세 개를 만들었고, 그 파일은 http:// 로 열어야만 동작했습니다. 그렇다면 누가 그 파일을 http:// 로 건네주는가? 그 일을 하는 프로그램이 웹서버이고, 오늘 쓰는 웹서버가 nginx입니다.

빌드는 물건을 만들고(그때 1회), 웹서버는 그 물건을 계속 나눠줍니다(상시 프로세스)

nginx가 하는 일의 본질은 단순합니다. 요청받은 URL 경로를, 자기가 맡은 폴더(root) 안의 파일 경로로 바꿔서 그 파일을 돌려준다. 이것을 정적 서빙이라고 합니다. 우리는 그 root 자리에 dist/ 를 꽂을 겁니다.

규칙은 하나 — URL 경로 = root 폴더 아래의 파일 경로. 마지막 줄의 “?”가 8번 섹션의 사건입니다

오늘 남은 시간에 겪을 사건 세 개가 전부 이 능력에서 나옵니다.

nginx의 능력무슨 일오늘 어디서 만나나
① 파일을 돌려준다URL → root 안의 파일 (위 그림)7번 — 그리고 없는 경로라면? → 404 사건 (8번)
② 헤더를 얹는다응답에 캐시 규칙 같은 지시문을 붙인다9번 — index.html 은 캐시 금지, assets/ 는 1년
③ 대신 전달한다특정 경로는 파일 대신 다른 서버로 넘긴다 (리버스 프록시)11번 — CORS가 사라지는 마법의 정체
“npm run dev 를 서버에 켜두면 안 되나요?”

개발 서버도 http:// 로 파일을 주긴 합니다. 하지만 그건 매 요청마다 소스 코드를 즉석에서 변환해 주는 개발 편의 도구입니다 — 느리고, 메모리를 많이 쓰고, 에러 메시지로 소스 구조가 노출됩니다.

nginx는 반대로 미리 구워둔 파일을 그대로 돌려주는 일만 합니다. 그래서 압도적으로 빠르고, 수천 명이 동시에 접속해도 버팁니다. “개발은 dev 서버, 배포는 웹서버” — 이 분업이 오늘의 전제입니다.

~/fe-study-2026 부분은 스터디 자료를 내려받은 위치로 바꾸세요. 잘 모르겠으면 자료 폴더에서 pwd 를 쳐서 나온 경로를 그대로 쓰시면 됩니다.

순서파일추가되는 것이 단계에서 겪는 일

1단계 설정으로 띄우기

터미널 — Windows PowerShell · 한 줄로 붙여 쓰세요

조각오늘 수준의 설명
nginx:alpinenginx가 설치된 작은 리눅스를 하나 빌려서 실행
--rm끄면 흔적 없이 치운다
-p 8080:80내 컴퓨터의 8080 → 그 안의 80으로 연결
-v …/dist:…/html:ro내 dist/ 를 그 안의 “웹 루트”에 읽기 전용으로 꽂아넣는다
-v …/nginx.conf:…/etc/nginx/conf.d/default.conf — nginx:alpine 이 기본으로 읽는 설정 파일 자리를 덮어쓴다

성공 기준

http://localhost:8080 에 접속했을 때 내 단어장 앱이 뜨면 됩니다. (nginx 기본 환영 페이지가 뜬다면 마운트 경로가 틀린 것입니다 — 아래 “자주 나는 에러” 참고)

8. /about 에서 새로고침 → 404

21:13 · 5분오늘의 두 번째 “문제 발생”

브라우저 주소창에 http://localhost:8080/about 을 직접 입력해 보세요.

브라우저 화면
404 Not Found
nginx/1.27.x

터미널에서도 똑같이 확인할 수 있습니다.

터미널 — 새 탭에서
curl -I http://localhost:8080/            # → HTTP/1.1 200 OK
curl -I http://localhost:8080/about       # → HTTP/1.1 404 Not Found
404가 떠야 정상입니다

안 뜬다면 설정 파일이 제대로 안 붙은 것입니다. nginx.conf 를 마운트했는지 확인하세요.

nginx.conf — 1단계 설정의 문제 지점
location / {
    #  $uri  : 요청 경로와 똑같은 이름의 파일을 찾아본다
    #  $uri/ : 디렉터리인지 찾아본다
    #  =404  : 둘 다 없으면 404 를 낸다
    try_files $uri $uri/ =404;
}
무슨 일이 일어났나
① 브라우저 → nginx    "GET /about 주세요"
      ▼
② nginx: $uri  → dist/about  파일을 찾음   → 없음
      ▼
③ nginx: $uri/ → dist/about/ 폴더를 찾음   → 없음
      ▼
④ =404 → 404 Not Found   없는 파일을 달라니 정직하게 404를 줍니다
핵심

/about 이라는 파일은 세상에 존재하지 않습니다. 존재하는 건 index.html 하나뿐이고, /about 은 그 안의 JavaScript가 만들어내는 가상의 주소입니다. nginx는 그 사정을 모릅니다.

“개발 서버에서는 잘 됐는데 배포하니까 404가 난다”의 정체가 이것입니다. Vite 개발 서버가 이 처리를 대신 해주고 있었을 뿐입니다. (npx serve dist 도 이걸 알아서 해줍니다. 그래서 serve 로는 이 실습이 안 됩니다.)

실무에서 이 버그가 악명 높은 이유 — “링크 클릭은 되는데 F5만 하면 깨진다”

실제 서비스에서는 라우터(react-router 등)가 /about 으로의 링크 이동을 JavaScript로 처리합니다. 서버에 요청이 아예 안 가니 클릭은 멀쩡합니다. 404는 새로고침 · 주소 직접 입력 · 링크 공유처럼 서버에 진짜 요청이 가는 순간에만 터집니다.

그래서 개발 중엔 안 보이다가 배포 후 사용자에게서 먼저 발견되는 단골 버그입니다. 직접 재현해 보고 싶은 분을 위해 과제의 선택 항목에 넣어두었습니다.

9. try_files 로 404 고치기

21:18 · 8분바뀌는 건 마지막 인자 하나

1단계 → 2단계, 이 한 군데가 전부입니다
# 1단계 nginx.conf
try_files $uri $uri/ =404;         # 파일 없으면 404

# 2단계 nginx-spa.conf
try_files $uri $uri/ /index.html;  # 파일 없으면 index.html 을 준다

try_files 는 왼쪽부터 순서대로 시도하고, 마지막 것은 무조건 준다로 읽으세요. /assets/index-C7xK9pQr.js 는 실제 파일이 있으니 그걸 주고, /about 은 없으니 index.html 을 줍니다. 그 다음은 React가 알아서 합니다.

같은 요청, 같은 판정 — 마지막 인자 하나가 결과를 가릅니다

2단계 설정으로 다시 띄우기

터미널 — 기존 컨테이너를 끄고 설정만 바꿔 다시 띄웁니다
docker stop study-web

docker run --rm -p 8080:80 \
  -v "$(pwd)/dist:/usr/share/nginx/html:ro" \
  -v "$(pwd)/nginx-spa.conf:/etc/nginx/conf.d/default.conf:ro" \
  --name study-web \
  nginx:alpine
터미널 — 새 탭에서 확인
curl -I http://localhost:8080/about       # → HTTP/1.1 200 OK  (404가 아니면 성공)
curl -I http://localhost:8080/index.html  # Cache-Control 헤더 확인
성공 기준

http://localhost:8080/about 에서 F5 를 눌러도 화면이 정상으로 나옵니다. curl -I 로는 404 → 200 으로 바뀐 것이 보입니다.

2단계에는 캐시 헤더도 같이 들어 있습니다

nginx-spa.conf — 2번 섹션의 “목차” 이야기가 설정이 된 부분
location = /index.html {
    add_header Cache-Control "no-cache, must-revalidate";
    try_files $uri =404;
}

location /assets/ {
    add_header Cache-Control "public, max-age=31536000, immutable";
    try_files $uri =404;
}
대상헤더이유
index.htmlno-cache, must-revalidate어떤 JS를 불러올지 적힌 목차 파일. 캐시되면 배포해도 안 바뀜
/assets/*public, max-age=31536000, immutable파일 이름에 해시가 붙어 있음. 내용이 바뀌면 이름이 바뀌므로 1년 캐시해도 안전

개발자도구 Network 탭에서 index.html 과 assets/index-*.js 를 각각 클릭하고 Response Headers 를 직접 확인해 보세요.

“그럼 진짜 없는 주소 /asdfasdf 는요?”

그것도 index.html 을 받습니다. 그리고 클라이언트가 404 화면을 그립니다. 404 판정의 책임이 서버에서 브라우저로 넘어간 것입니다 — 4회차 SEO 이야기의 씨앗입니다.

서버가 거부한 게 아닙니다. 요청은 갔고 응답도 왔습니다. 브라우저가 그 응답을 내 JavaScript에게 안 넘겨준 것입니다.

② 애초에 같은 출처로 만든다리버스 프록시프론트 배포 설정만으로 해결. 오늘은 이 길로 갑니다

11. 리버스 프록시 — CORS를 없애기

21:34 · 12분오늘 심화의 핵심

nginx-proxy.conf — 이 한 블록이 추가됐습니다
location /api/ {
    proxy_pass http://mini-api:3001;

    proxy_set_header Host              $host;
    proxy_set_header X-Real-IP         $remote_addr;
    proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}

location / {
    try_files $uri $uri/ /index.html;
}
nginx ↔ mini-api 구간은 서버끼리의 통신 — CORS는 브라우저 정책이라 이 구간에는 개념 자체가 없습니다
2회차 복선 회수 — Vite proxy와 같은 그림입니다

2회차 개발 서버의 vite.config.js proxy가 정확히 이 역할이었습니다. “빌드하면 Vite가 없다. 그럼 누가 해주지?” — 그 답이 지금 이 그림입니다. 개발에서는 Vite가, 배포에서는 nginx가 같은 자리에 서 있습니다.

⚠️ 오늘 가장 많이 나올 사고 — 단독 실행하면 즉사합니다

이 설정을 docker run 으로 혼자만 띄우면 컨테이너가 뜨자마자 죽습니다.

nginx: [emerg] host not found in upstream "mini-api"

nginx는 시작할 때 upstream 이름을 한 번에 해석하는데, mini-api 는 같은 docker 네트워크 안의 컨테이너 이름(또는 compose 서비스 이름)이라서 그 밖에서는 존재하지 않는 이름이기 때문입니다.

그래서 아래 순서대로 하셔야 합니다. mini-api 컨테이너가 먼저입니다.

① 네트워크를 만들고, mini-api를 그 안에 컨테이너로 띄웁니다

아까 node server.js 로 띄운 미니 API는 먼저 Ctrl + C 로 끄세요. 이번에는 컨테이너로 띄웁니다.

터미널 — 두 컨테이너가 서로를 이름으로 찾을 수 있게 합니다

docker build -t mini-api .
docker run -d --rm --network study-net --name mini-api mini-api

docker logs -f mini-api     # 로그를 띄워두세요. 프록시 동작의 증거가 여기 찍힙니다
--name mini-api 를 반드시 지키세요

이 이름이 nginx-proxy.conf 의 proxy_pass http://mini-api:3001; 과 글자 하나까지 같아야 합니다. 같은 네트워크 안에서는 컨테이너 이름이 곧 호스트 이름입니다.

② nginx를 같은 네트워크에 3단계 설정으로 띄웁니다

터미널 — 다시 dist 가 있는 폴더에서
docker stop study-web

docker run --rm -p 8080:80 \
  --network study-net \
  -v "$(pwd)/dist:/usr/share/nginx/html:ro" \
  -v "$(pwd)/nginx-proxy.conf:/etc/nginx/conf.d/default.conf:ro" \
  --name study-web \
  nginx:alpine

③ 프론트엔드는 호스트를 아예 적지 않습니다

.env — 값을 비웁니다
VITE_API_URL=
그러면 요청 주소가 이렇게 바뀝니다
// 변경 전 — 호스트와 포트를 직접 적음 (= 다른 출처 = CORS 대상)
fetch('http://localhost:3001/api/words')

// 변경 후 — 호스트를 아예 적지 않음 (= 지금 보고 있는 사이트에 그대로 요청)
fetch('/api/words')
터미널 — 오늘 세 번째 재빌드입니다
npm run build

④ 확인 — 증거는 세 군데에 있습니다

터미널
curl -i http://localhost:8080/api/health   # {"status":"ok"}
curl -i http://localhost:8080/api/words    # 단어 JSON 8개
프록시 전프록시 후

가장 확실한 증거 — mini-api 로그

브라우저 주소창에는 3001 이라는 포트가 한 번도 등장하지 않는데 mini-api 터미널에는 요청이 찍힙니다. nginx가 대신 전달해 준 것입니다.

📸 오늘의 결론

미니 API 코드는 한 글자도 안 고쳤습니다. CORS 헤더는 지금도 하나도 없습니다. 바뀐 건 nginx.conf 몇 줄과 .env 한 줄뿐입니다.

CORS를 “해결”한 게 아니라 “발생하지 않게 만든” 것입니다. 브라우저 입장에서 화면도 API도 전부 http://localhost:8080 한 곳이니 교차 출처라는 상황 자체가 생기지 않습니다. (nginx ↔ mini-api 는 서버끼리의 통신이라 CORS라는 개념 자체가 없습니다.)

끝의 슬래시 하나로 동작이 달라집니다

proxy_pass http://mini-api:3001; → GET /api/words 를 그대로 전달 ✅

proxy_pass http://mini-api:3001/; → /api 를 떼고 GET /words 로 전달 ❌ 404

순서는 걱정 안 하셔도 됩니다. nginx는 순서가 아니라 가장 긴 접두사 우선이라 /api/ 가 / 를 이깁니다.

정리 — 실습이 끝나면

터미널
docker stop study-web mini-api
docker network rm study-net
참고 — docker compose 로 하는 방법 (4회차와 같은 방식)

저장소의 docker/ 폴더에 docker-compose.yml 이 준비돼 있습니다. 이 방식에서는 두 컨테이너가 자동으로 같은 네트워크에 올라가고 서비스 이름 mini-api 가 그대로 호스트 이름이 됩니다. 다만 포트가 8080이 아니라 80(http://localhost)입니다. 다음 주에 이걸 직접 만듭니다.

✅ 오늘의 결과물 완성

자주 나는 에러 — 실습 내내 이 목록을 열어두세요

포트가 이미 사용 중 (address already in use / port is already allocated)

미니 API 쪽 — 3001 포트를 다른 프로세스가 쓰는 중입니다.

Error: listen EADDRINUSE: address already in use :::3001
lsof -i :3001              # macOS/Linux — 누가 쓰는지 확인 후 종료
netstat -ano | findstr :3001   # Windows

PORT=4000 node server.js   # 또는 포트를 바꿔서 실행

nginx 쪽 — 8080 포트를 다른 컨테이너가 쓰는 중입니다.

Bind for 0.0.0.0:8080 failed: port is already allocated
docker ps                  # 뭐가 떠 있는지 확인
docker stop study-web      # 이전 실습 컨테이너가 남아 있는 경우가 대부분

-p 8081:80                 # 그래도 안 되면 포트만 바꿔서 진행하세요

원인 추적하다가 시간 다 갑니다. 포트를 바꿔서 넘어가세요.

nginx: [emerg] host not found in upstream "mini-api"

원인: nginx-proxy.conf 를 단독으로 띄웠습니다. nginx는 시작할 때 upstream 이름을 한 번에 해석하는데, mini-api 라는 이름이 존재하지 않아 시작하자마자 죽습니다. 화면조차 안 뜹니다. 이건 문법 오류가 아니라 네트워크 문제입니다.

해결 — 셋 중 하나:

  • ① 순서를 지킨다 — docker network create study-net 후 --network study-net --name mini-api 로 API를 먼저 띄우고, nginx도 같은 네트워크로 (오늘 방식)
  • ② compose 로 함께 띄운다 — docker compose up --build (다음 주 방식)
  • ③ 프록시 없이 화면만 보고 싶으면 — nginx-proxy.conf 의 location /api/ { … } 블록을 통째로 주석 처리
지금 mini-api 가 떠 있는지 확인
docker ps                  # NAMES 칸에 mini-api 가 보여야 합니다
docker logs mini-api
docker logs study-web      # nginx 가 왜 죽었는지
환경변수를 바꿨는데 화면에 반영이 안 됨

원인: 재빌드를 안 했습니다. 오늘의 핵심 그 자체입니다. VITE_* 는 “실행할 때 읽는 값”이 아니라 “빌드할 때 코드에 박히는 텍스트”입니다. dist/ 는 이미 구워진 파일 더미라서, 실행 시점에는 .env 를 아무도 읽지 않습니다.

확인 순서
npm run build                      # ① 재빌드했는가
grep -r "바꾼값" dist/              # ② 정말 박혔는지 눈으로 확인
                                   #    브라우저 새로고침 (캐시 비우고 강력 새로고침)

그래도 undefined 라면 세 가지를 순서대로 확인하세요.

  • 접두사 — VITE_ 로 시작하지 않으면 주입되지 않습니다
  • 파일 위치 — .env 는 package.json 과 같은 폴더여야 합니다
  • 개발 서버 — npm run dev 중이었다면 껐다 켜야 합니다
dist/index.html 을 더블클릭하면 흰 화면

정상입니다. 고칠 필요 없습니다. 3번 섹션에서 일부러 겪은 그 화면입니다.

원인 두 가지가 동시에 — ① index.html 안의 /assets/… 는 절대 경로라서 file:// 에서는 디스크 최상위를 가리킵니다. ② <script type="module"> 은 보안 정책상 file:// 에서 실행되지 않습니다.

해결 — 웹서버로 열면 됩니다
npx -y serve dist          # → http://localhost:3000

주소창을 보세요. file:// 이면 파일을 연 것이고, http:// 면 서버에게 요청한 것입니다. 우리 앱은 후자를 전제로 만들어졌습니다.

CORS 에러 메시지 읽는 법
한 줄씩 나눠서 읽습니다
Access to fetch at 'http://localhost:3001/api/words'     ← ① 어디로 요청했나
from origin 'http://localhost:8080'                       ← ② 지금 열려 있는 페이지
has been blocked by CORS policy:                          ← ③ 막은 주체 = 브라우저
No 'Access-Control-Allow-Origin' header is present         ← ④ 응답에 허락 헤더가 없다

①과 ②의 포트가 다르면 그게 원인입니다. 출처는 프로토콜 + 호스트 + 포트이고, 포트만 달라도 다른 출처입니다.

서버 에러가 아닙니다. mini-api 터미널을 보세요 — GET /api/words -> 200 이 찍혀 있습니다. 요청은 갔고 서버는 응답했습니다. 브라우저가 그 응답을 내 JS에게 안 넘겨준 것뿐입니다. 그래서 curl 로는 잘 됩니다.

해결: 11번 섹션의 리버스 프록시. 프록시를 붙였는데도 에러가 남아 있다면 fetch 주소가 아직 localhost:3001 인 것입니다 — .env 를 비우고 재빌드했는지 확인하세요.

컨테이너는 떴는데 nginx 기본 환영 페이지가 보임

원인: -v 마운트 경로가 틀렸습니다. dist 가 안 꽂힌 것입니다.

확인
pwd                        # dist 가 있는 폴더에서 실행하고 있는지
ls dist                    # index.html, assets/ 가 보이는지

docker exec study-web ls /usr/share/nginx/html
docker exec study-web cat /etc/nginx/conf.d/default.conf

Windows에서 마운트가 빈 폴더로 보인다면 Docker Desktop → Settings → Resources → File Sharing 설정을 확인하세요. 급하면 짝꿍 노트북으로 진행하시는 게 빠릅니다.

설정을 고쳤는데 반영이 안 된다면 — nginx는 시작할 때 설정을 읽습니다. 컨테이너를 껐다 다시 띄우세요 (docker stop study-web → docker run …).

Unexpected token '<', "<!doctype "... is not valid JSON

원인: API 요청이 프록시로 안 가고 index.html 로 샜습니다. JSON인 줄 알았는데 HTML이 온 것입니다.

  • location /api/ 블록이 있는 설정 파일을 마운트했는지 — nginx-spa.conf 를 붙여둔 채 API를 부르고 있지 않은지 확인하세요
  • 요청 경로가 /api/ 로 시작하는지 (Network 탭의 Request URL)

반대로 /api/words 가 404 라면 proxy_pass 끝에 / 를 붙였을 가능성이 큽니다. 붙이면 /api 를 떼고 전달합니다. 슬래시를 빼세요.

필수 1 — nginx 설정 바꿔보기

  • (a) try_files 의 마지막 인자를 /index.html → =404 로 바꿔서 동작이 어떻게 달라지는지 한 문장으로 적고, 되돌려 놓기
  • (b) location = /healthz 로 헬스체크 응답을 만들고, = 가 무슨 뜻인지 한 줄로 적기
힌트 — 이 두 줄이면 됩니다
location = /healthz {
    return 200 "ok\n";
}
= 가 붙으면 무엇이 달라지나

location /healthz 는 접두사 일치(/healthz/abc 도 걸림), location = /healthz 는 정확히 일치하는 그 경로 하나만 걸립니다. 그리고 nginx는 = 를 가장 높은 우선순위로 처리합니다. nginx-spa.conf 의 location = /index.html 이 같은 이유로 쓰였습니다.

필수 2 — 캐시 헤더 실험

  1. 개발자도구 Network 탭에서 Disable cache 체크를 해제합니다
  2. assets/index-*.js 를 클릭 → Response Headers 에 max-age=31536000, immutable 이 있는지 확인
  3. 두 번째 새로고침에서 Size 칼럼이 (disk cache) 로 바뀌는지 확인
  4. 컴포넌트를 아무거나 고치고 npm run build → 파일명(해시)이 바뀌고 새로 받아지는지 확인
이 실험의 요점

해시가 붙은 파일은 내용이 바뀌면 이름이 바뀌기 때문에 1년을 캐시해도 안전합니다. 반대로 index.html 은 나머지 전부의 목차라서 절대 캐시하면 안 됩니다.

선택 (여유 있으신 분)

  • npm install react-router-dom 으로 /about 라우트를 하나 만들어 “링크 클릭은 성공, F5는 404”를 직접 재현해 보기 — 1단계 설정(nginx.conf)으로 띄운 상태에서만 재현됩니다. 2단계로 바꾸면 사라지는 것까지 확인하면 완벽합니다
  • 2회차부터 쓰고 있던 vite.config.js 의 server.proxy 를 다시 열어 오늘의 nginx-proxy.conf 와 어느 줄이 어느 줄에 대응되는지 표로 적어 오기 — 개발의 Vite, 배포의 nginx가 같은 자리라는 것을 손으로 확인하는 과제입니다
  • gzip on; 을 껐다 켜면서 Network 탭의 전송량 비교하기
  • .env.production 과 --mode 로 환경별 빌드 나눠보기
