✅ 여기까지 확인

1. fetch — 에디터를 아직 열지 마세요

19:15 · 10분먼저 주소창에, 그다음 콘솔에

API도 그냥 웹페이지입니다. 주소창에 쳐보면 그대로 보입니다. 오늘의 데이터는 함께 제공되는 미니 API 서버(로컬)에서 옵니다 — 회원가입도, API 키도, 인터넷도 필요 없습니다.

브라우저 주소창
http://localhost:5173/api/words/serendipity

예쁘게 꾸며진 HTML 대신 JSON이 쏟아집니다. 사람이 아니라 컴퓨터가 읽으라고 만든 웹페이지이기 때문입니다.

이제 콘솔에서 — 한 줄 치고, 엔터, 결과 읽고, 다음 줄

F12 → Console
const res = await fetch('/api/words/serendipity')
res.status     // 200
res.ok         // true
const data = await res.json()
data
왜 두 번 기다리나

① await fetch(...) = 헤더가 왔다. 이때 상태 코드를 알 수 있습니다.

② await res.json() = 본문을 끝까지 받아 해석했다.

덕분에 “본문을 받기 전에 404인 걸 알고 일찍 포기”할 수 있습니다.

이번엔 없는 단어로 — 오늘 가장 중요한 실험

F12 → Console
const res404 = await fetch('/api/words/notaword123')
res404.status          // 404
res404.ok              // false
← 그런데 예외는 하나도 안 던져졌습니다
오늘 반복해서 나올 문장 ①

fetch 는 404도 성공으로 칩니다. “답장이 왔다”는 사실 자체를 성공으로 봅니다. 404도 성공, 500도 성공입니다.

fetch 가 진짜로 예외를 던지는 경우는 이것뿐입니다 — 인터넷이 끊겼다 · 존재하지 않는 도메인이다 · CORS로 브라우저가 막았다 · 요청이 취소되었다.

그래서 try/catch 만 써놓고 “에러 처리 했다”고 생각하면 안 됩니다. res.status 와 res.ok 는 우리가 직접 봐야 합니다.

2. async/await 와 응답 구조

19:25 · 10분await 를 빼면 어떻게 되나

F12 → Console

// Promise { <pending> }   "아직 안 끝난 일"이라는 빈 상자입니다
오늘은 여기까지만

await 는 시간이 걸리는 일 앞에 붙이는 “다 될 때까지 기다려” 표시입니다. 그리고 await 를 쓰려면 그 함수가 async function 이어야 합니다. 이벤트 루프는 오늘 주제가 아닙니다.

응답 구조 — 그리고 404는 모양이 다릅니다

콘솔에서 점을 하나씩 찍어 내려가 보세요. data → data.word → data.meaning → …

응답 구조
성공(200):                          실패(404):
{                                   {
  word: "serendipity",               error: "Word not found",
  phonetic: "/ˌser.ənˈdɪp.ə.ti/",    word: "notaword123",
  partOfSpeech: "명사",               hint: "GET /api/words 로 …"
  meaning: "뜻밖의 행운을 …",        }

참고 — 진짜 인터넷 사전은 더 험합니다

선택 과제에서 붙여볼 진짜 사전 API(dictionaryapi.dev)는 응답이 세 겹 중첩 배열(data[0].meanings[0].definitions[0].definition)입니다. 오늘 flat 구조로 기본기를 잡고, 험한 구조는 선택 과제에서 만나세요.

3. 로딩 · 에러 · 데이터 — 하나의 요청, 세 가지 상태

19:35 · 15분먼저 무한 루프를 터뜨립니다

⚠️ Network 탭을 열고 시작하세요. 그리고 20초 안에 되돌립니다

콘솔에는 아무 에러도 안 납니다. Network 탭을 안 열면 “잘 되는 줄” 압니다.

src/App.jsx — ❌ 일부러 틀리는 코드
export default function App() {
  const [result, setResult] = useState(null)

  fetch('/api/words/serendipity')
    .then((res) => res.json())
    .then((data) => setResult(data))

  // 저장 → Network 탭이 폭포처럼 흘러내립니다
}
왜 그런가 — 판서하세요

① 컴포넌트 함수가 실행된다 → ② fetch 가 출발한다 → ③ 응답 도착 → setResult(...) → ④ state가 바뀌었으니 다시 실행 → ⑤ ①로 돌아간다.

컴포넌트 함수의 본체는 “화면을 계산하는 곳”이지 “일을 시키는 곳”이 아닙니다. 요청·타이머·저장은 렌더가 끝난 뒤에 따로 해야 하고, 그 “따로”의 이름이 useEffect 입니다.

useEffect 해부

모양
useEffect(() => {
  // ① 렌더가 화면에 반영된 "뒤에" 실행할 일
  return () => {
    // ③ 정리(cleanup). 다음 실행 직전과, 컴포넌트가 사라질 때
  }
}, [의존성, 배열])
//  ② "이 값들이 지난번과 다르면 ①을 다시 실행해라"
쓰는 법언제 실행되나오늘 쓰는 곳
useEffect(fn)매 렌더마다. 거의 안 씁니다안 씀
useEffect(fn, [])처음 한 번만지금 이 단계
useEffect(fn, [query])처음 + query 가 바뀔 때마다4번 검색 실습
가장 나쁜 습관 — 경고 없애려고 배열을 비우기

의존성 배열은 “얼마나 자주 실행할까”를 정하는 옵션이 아닙니다. “이 effect 안에서 쓰는 바깥 값들의 목록”입니다. 여기를 [] 로 두면 다음 단계에서 검색어를 바꿔도 화면이 안 바뀝니다.

요청이 정확히 2번 가는 것 — StrictMode

개발 모드에서 React가 일부러 effect를 한 번 더 실행합니다. 고장이 아니라 검사기입니다. “두 번 실행해도 앱이 멀쩡한가?”를 검사하는 것이고, 오늘 마지막 40분에 이게 왜 고마운지 알게 됩니다. 절대 StrictMode 를 지우지 마세요.

세 가지 상태를 코드로 — 오늘 기초 파트의 핵심

요청 하나의 세 가지 상태
① loading  아직 모른다        → "🔍 찾는 중…"
② error    실패로 끝났다      → 사람이 읽을 수 있는 안내 + 다음 행동
③ data     성공으로 끝났다    → 결과 화면
규칙 ①

셋 중 정확히 하나만 화면에 보여야 한다.

규칙 ②

새 요청을 시작할 때 error 와 data 를 반드시 비운다. 안 비우면 “이전 에러 문구 아래에 새 결과”가 같이 뜹니다.

규칙 ③ — 실무 1등 버그

성공하든 실패하든 loading 은 반드시 꺼진다. 여기를 빠뜨리면 “영원히 찾는 중” 화면이 됩니다. 원인은 항상 에러 경로의 setLoading(false) 누락입니다.

src/App.jsx — 일단 단어 하나를 고정으로 검색해 봅니다
import { useState, useEffect } from 'react'
import WordList from './components/WordList.jsx'
import { WORDS } from './data/words.js'

const BASE_URL = '/api/words'

export default function App() {
  const [words, setWords] = useState(WORDS)

  const [result, setResult] = useState(null)
  const [loading, setLoading] = useState(true)   // 다음 단계에서 false 로 바꿉니다
  const [error, setError] = useState(null)

  useEffect(() => {
    // useEffect 의 콜백은 cleanup 함수를 돌려줘야 합니다.
    // async 함수는 Promise 를 돌려주므로 콜백 자체를 async 로 만들 수 없습니다.
    async function run() {
      setLoading(true); setError(null); setResult(null)   // 규칙 ②
      try {
        const res = await fetch(`${BASE_URL}/serendipity`)

        if (res.status === 404) {
          throw new Error('사전에서 찾을 수 없습니다. 철자를 확인해 주세요.')
        }
        if (!res.ok) {
          throw new Error(`API 서버가 응답하지 않습니다. (${res.status})`)
        }

        const json = await res.json()

        setResult({
          id: `${json.word}-${Date.now()}`,
          word: json.word,
          phonetic: json.phonetic ?? '',
          partOfSpeech: json.partOfSpeech,
          meaning: json.meaning,
          example: json.example ?? '',
        })
        setLoading(false)                                   // 규칙 ③
      } catch (err) {
        setError(err.message)
        setLoading(false)                                   // 규칙 ③
      }
    }

    run()
  }, [])

  return (
    <>
      <header className="page-header">
        <h1 className="page-title">나만의 단어장</h1>
        <p className="page-subtitle">저장된 단어 {words.length}개</p>
      </header>

      <section className="search-panel">
        {loading && <p className="status status-loading">🔍 찾는 중…</p>}
        {error && <p className="status status-error">⚠️ {error}</p>}
        {result && <p className="search-result-meaning">{result.meaning}</p>}
      </section>

      <WordList words={words} />
    </>
  )
}

4. 검색창 — 지난주 폼이 SearchBar 가 됩니다

20:20 · 15분새로 배우는 게 하나도 없습니다

useState 로 입력값을 잡고, onSubmit 에서 preventDefault 하고, 부모가 준 함수를 부릅니다. 지난주 구조와 완전히 같습니다.

src/components/SearchBar.jsx (새 파일)
import { useState } from 'react'

export default function SearchBar({ onSearch }) {
  const [input, setInput] = useState('')

  function handleSubmit(event) {
    // 이 한 줄을 빼면 폼의 원래 동작(페이지 새로고침)이 일어납니다.
    // 새로고침되면 state 가 전부 초기화되어 앱이 처음 상태로 돌아갑니다.
    event.preventDefault()

    const trimmed = input.trim()
    if (trimmed === '') return

    // 사전 API 는 소문자 기준으로 찾는 편이 안전합니다.
    onSearch(trimmed.toLowerCase())
  }

  return (
    <form className="search-bar" onSubmit={handleSubmit}>
      <input
        className="search-input"
        value={input}
        onChange={(event) => setInput(event.target.value)}
        placeholder="영어 단어를 검색하세요 (예: serendipity)"
      />
      <button className="search-submit" type="submit">
        검색
      </button>
    </form>
  )
}

경쟁 상태 (race condition)

화면은 “마지막에 도착한 것”을 그립니다. 우리가 원하는 건 “마지막에 요청한 것”입니다. 이 둘이 어긋나는 것입니다.

“먼저 보낸 요청이 먼저 도착한다”는 것은 어디에도 보장돼 있지 않습니다. 캐시, 서버 부하, 네트워크 상태에 따라 순서는 언제든 뒤바뀝니다.

핵심 문장 — 판서

setResult(x) 를 쓰기 전에 물어야 합니다 — “지금 이 응답이 아직 유효한가?”

그 질문에 답하는 장치가 cleanup 입니다.

해결 ① — ignore 플래그: 결과를 버린다

핵심 — effect 가 실행될 때마다 ignore 가 “새로” 만들어집니다

① effect(apple) → 자기만의 ignore(A) = false, 요청 A 출발

② 검색어가 바뀌면 React가 먼저 cleanup(apple) 을 호출 → ignore(A) = true

③ 그다음 effect(banana) → 별개의 ignore(B) = false

④ B 도착 → 자기 ignore는 false → 화면 갱신 ✅   ⑤ A 도착 → 자기 ignore는 true → 그냥 return ✅

변수가 하나가 아니라 실행마다 새로 생깁니다. 그래서 B가 A의 ignore 를 건드릴 일이 없습니다.

StrictMode 가 왜 고마웠나

StrictMode 는 개발 모드에서 effect 실행 → cleanup → 다시 실행 을 합니다. cleanup 을 안 짜놨으면 개발 중에 이미 이상하게 동작했을 겁니다. 아까부터 이 버그를 미리 보여주려고 그러고 있었던 것입니다.

일단 ignore 로 시작하고, 요청이 비싸지면 AbortController 를 얹습니다. 둘을 같이 써도 됩니다 — 다음 단계에서 만들 훅에서는 실제로 둘 다 씁니다.

React 만의 문제가 아닙니다

검색 자동완성, 탭 전환, 무한 스크롤, 필터 여러 개 빠르게 바꾸기, 지도 확대/축소 — “비동기 작업 여러 개 + 마지막 것만 유효”인 모든 상황에서 똑같이 납니다.

그리고 경쟁 상태는 개발자 환경에서 거의 안 터집니다. localhost는 빠르고, 개발자는 자기 앱을 천천히 씁니다. 재현이 안 되는 버그를 만나면 타이밍을 먼저 의심하세요. 로직 버그는 재현됩니다.

최종 코드 ① — useWordSearch.js

src/hooks/useWordSearch.js (새 파일)
import { useState, useEffect } from 'react'

const BASE_URL = '/api/words'

// API 응답을 우리 앱이 쓰는 단어 모양으로 "번역"합니다.
// 지금은 응답이 flat 이라 하는 일이 id 붙이기 정도지만,
// 선택 과제의 진짜 사전 API(세 겹 배열)로 갈아끼울 때
// 이 함수 하나만 바뀌고 앱의 나머지는 그대로입니다.
function toWord(json) {
  return {
    // 같은 단어를 또 추가해도 목록 key 가 겹치지 않게 시각을 붙입니다
    id: `${json.word}-${Date.now()}`,
    word: json.word,
    phonetic: json.phonetic ?? '',
    partOfSpeech: json.partOfSpeech,
    meaning: json.meaning,
    example: json.example ?? '',
  }
}

export function useWordSearch(word) {
  const [data, setData] = useState(null)
  const [loading, setLoading] = useState(false)
  const [error, setError] = useState(null)

  useEffect(() => {
    // 아직 아무것도 검색하지 않은 상태입니다.
    // 상태를 깨끗이 비우고 요청은 보내지 않습니다.
    if (word === '') {
      setData(null)
      setError(null)
      setLoading(false)
      return
    }

    let ignore = false
    const controller = new AbortController()

    // 새 요청을 시작할 때 이전 결과와 이전 에러를 반드시 비웁니다.
    setLoading(true)
    setError(null)
    setData(null)

    async function run() {
      try {
        const res = await fetch(`${BASE_URL}/${encodeURIComponent(word)}`, {
          signal: controller.signal,
        })

        // ★★★ fetch 는 404 를 예외로 던지지 않습니다 ★★★
        // 404 응답은 성공과 모양이 다른 { error, word, hint } 객체입니다.
        if (res.status === 404) {
          throw new Error(
            `'${word}' 은(는) 단어장 사전에 없습니다. 다른 단어를 검색해 보세요.`
          )
        }

        // 이 사전 API 는 간헐적으로 502 를 뱉습니다. 우리 코드 버그가 아닙니다.
        if (!res.ok) {
          throw new Error(
            `API 서버가 응답하지 않습니다. (${res.status}) 미니 API 서버가 켜져 있는지 확인하세요.`
          )
        }

        const json = await res.json()
        const found = toWord(json)

        // 이 응답이 아직 유효한가? 낡았으면 화면을 건드리지 않습니다.
        if (ignore) return
        setData(found)
        setLoading(false)
      } catch (err) {
        // 내가 취소한 것은 "에러"가 아닙니다. 조용히 빠져나갑니다.
        if (ignore || err.name === 'AbortError') return
        setError(err.message)
        setLoading(false)
      }
      // ⚠️ 여기에 finally { setLoading(false) } 를 쓰면 안 됩니다.
    }

    run()

    // cleanup — 다음 effect 시작 직전, 그리고 컴포넌트가 사라질 때
    return () => {
      ignore = true
      controller.abort()
    }
  }, [word])

  return { data, loading, error }
}

src/App.jsx — 오늘의 최종본
import { useState, useEffect } from 'react'
import SearchBar from './components/SearchBar.jsx'
import StatusMessage from './components/StatusMessage.jsx'
import WordList from './components/WordList.jsx'
import { useWordSearch } from './hooks/useWordSearch.js'
import { WORDS } from './data/words.js'

const STORAGE_KEY = 'my-vocabulary'

function loadWords() {
  const saved = localStorage.getItem(STORAGE_KEY)
  if (saved === null) return WORDS

  try {
    const parsed = JSON.parse(saved)
    return Array.isArray(parsed) ? parsed : WORDS
  } catch {
    return WORDS
  }
}

export default function App() {
  const [words, setWords] = useState(loadWords)
  const [query, setQuery] = useState('')

  // 검색에 필요한 로직은 전부 커스텀 훅 안에 있습니다.
  const { data: result, loading, error } = useWordSearch(query)

  useEffect(() => {
    localStorage.setItem(STORAGE_KEY, JSON.stringify(words))
  }, [words])

  const alreadyAdded =
    result !== null && words.some((item) => item.word === result.word)

  function handleAdd() {
    if (result === null) return
    if (alreadyAdded) return

    setWords([{ id: Date.now(), ...result }, ...words])
    setQuery('')
  }

  function handleDelete(id) {
    setWords(words.filter((item) => item.id !== id))
  }

  return (
    <>
      <header className="page-header">
        <h1 className="page-title">나만의 단어장</h1>
        <p className="page-subtitle">저장된 단어 {words.length}개</p>
      </header>

      <SearchBar onSearch={setQuery} />

      <section className="search-panel">
        <StatusMessage loading={loading} error={error} />

        {result && (
          <div className="search-result">
            <div className="search-result-head">
              <h2 className="search-result-word">{result.word}</h2>
              {result.phonetic && (
                <span className="search-result-pron">{result.phonetic}</span>
              )}
              <span className="card-pos">{result.partOfSpeech}</span>
            </div>

            <p className="search-result-meaning">{result.meaning}</p>
            {result.example && (
              <p className="search-result-example">{result.example}</p>
            )}

            <button
              className="search-result-add"
              onClick={handleAdd}
              disabled={alreadyAdded}
            >
              {alreadyAdded ? '이미 단어장에 있습니다' : '내 단어장에 추가'}
            </button>
          </div>
        )}
      </section>

      {words.length === 0 ? (
        <StatusMessage
          empty
          emptyText="단어장이 비어 있습니다. 위에서 단어를 검색해 추가해 보세요."
        />
      ) : (
        <WordList words={words} onDelete={handleDelete} />
      )}
    </>
  )
}

10. 자주 나는 에러

막히면 여기부터 보세요. 그래도 안 되면 손을 들어주세요.

fetch 는 404를 에러로 안 던집니다 — 없는 단어인데 앱이 터져요

원인: try/catch 만 써놓고 “에러 처리 했다”고 생각한 것입니다. fetch 는 “답장이 왔다”는 사실 자체를 성공으로 칩니다. 404도 성공, 500도 성공입니다.

고치는 법 — res.status / res.ok 를 직접 봅니다
const res = await fetch(url)
const json = await res.json()      ← 404 인데 그냥 통과합니다

const res = await fetch(url)
if (res.status === 404) throw new Error('사전에서 찾을 수 없습니다.')
if (!res.ok) throw new Error(`API 서버가 응답하지 않습니다. (${res.status})`)
const json = await res.json()

fetch 가 진짜로 예외를 던지는 경우는 이것뿐입니다 — 인터넷 끊김 · 없는 도메인 · CORS 차단 · 요청 취소.

TypeError: Cannot read properties of undefined

원인: 응답이 내가 기대한 모양이 아닙니다. 404일 때 서버는 단어 객체가 아니라 { error, word, hint } 객체를 돌려줍니다. 그래서 json.meaning 이 undefined 가 되고, 거기에 .length 같은 걸 찍으면 터집니다.

확인하는 법
// 터지는 줄 바로 위에 한 줄 넣고 콘솔을 보세요
console.log(json)

// { error: ... } 모양이 찍히면 → 404 를 안 걸러낸 것입니다

고치는 법: 위 항목의 res.status === 404 검사를 먼저 넣으세요. 그리고 phonetic · example 처럼 없을 수도 있는 값에는 ?? '' 를 붙입니다.

useEffect 무한 루프 — Network 탭이 폭포처럼 흘러내립니다

원인 두 가지 중 하나입니다.

① 의존성 배열을 아예 안 썼다
useEffect(() => { run() })          ← 매 렌더마다 실행 → setState → 다시 렌더 → …
useEffect(() => { run() }, [query])
② effect 밖, 컴포넌트 본체에 fetch 를 썼다
export default function App() {
  fetch('...').then(...).then((d) => setResult(d))    ← 렌더할 때마다 실행됩니다
}

컴포넌트 함수의 본체는 “화면을 계산하는 곳”이지 “일을 시키는 곳”이 아닙니다. 요청·타이머·저장은 useEffect 안으로 넣으세요.

참고: 요청이 정확히 2번 가는 것은 무한 루프가 아니라 StrictMode 의 의도된 동작입니다. 정상입니다.

localStorage 에 객체를 넣었더니 '[object Object]' 가 나옵니다

원인: localStorage 는 문자열만 담는 서랍입니다. 객체를 그냥 넣으면 자바스크립트가 억지로 문자열로 바꾸면서 '[object Object]' 라는 쓸모없는 글자가 됩니다.

고치는 법 — 항상 짝으로 씁니다
localStorage.setItem('my-vocabulary', words)              ← '[object Object]'

localStorage.setItem('my-vocabulary', JSON.stringify(words))
const parsed = JSON.parse(localStorage.getItem('my-vocabulary'))

넣을 때 stringify, 꺼낼 때 parse. 한쪽만 하면 반드시 깨집니다.

이미 꼬였다면 콘솔에서 localStorage.clear() 하고 새로고침하세요.

영원히 “🔍 찾는 중…” 에서 멈춰 있습니다

원인: 에러 경로의 setLoading(false) 누락입니다. 실무 1등 버그이기도 합니다.

성공 경로에만 setLoading(false) 를 써놓으면 요청이 실패하는 순간 로딩이 영원히 안 꺼집니다. catch 블록에도 반드시 넣으세요.

⚠️ 다만 finally { setLoading(false) } 로 몰아 쓰면 안 됩니다. 취소된 옛 요청의 finally 도 실행되면서 “로딩 중인데 로딩 표시가 꺼진 화면”이 됩니다.

검색어를 바꿔도 화면이 안 바뀝니다

원인: 의존성 배열이 [] 로 남아 있습니다. [] 는 “처음 한 번만 실행해라”라는 뜻입니다.

고치는 법
}, [])          ← 처음 한 번만
}, [query])     ← query 가 바뀔 때마다

의존성 배열은 실행 횟수 옵션이 아니라 “이 effect 안에서 쓰는 바깥 값들의 목록”입니다. 경고를 없애려고 배열을 비우지 마세요.

검색하면 “API 서버가 응답하지 않습니다 (500)” 가 뜹니다

십중팔구 터미널 1(미니 API 서버)이 꺼진 것입니다. proxy가 전달할 곳(3001)이 없으면 500 을 돌려줍니다.

node server.js

검색이 계속 실패합니다 / 화면이 하얗습니다

  • 진짜 인터넷 사전 붙이기 — useWordSearch.js 의 BASE_URL 을 https://api.dictionaryapi.dev/api/v2/entries/en 으로 바꾸고, toWord() 를 세 겹 배열(json[0].meanings[0].definitions[0]) 기준으로 고쳐 보세요. 고칠 파일이 이 하나뿐이라면 성공 — “번역 층”이 제대로 서 있는 것입니다. ⚠️ 이 API는 자주 죽습니다(504/522). 안 될 때 여러분의 에러 화면이 대신 말해주면, 그것도 성공입니다
